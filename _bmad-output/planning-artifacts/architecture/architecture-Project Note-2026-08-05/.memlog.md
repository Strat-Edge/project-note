- (decision) Mode coaching. Purpose confirmé : build-substrate pur, aucun livrable de présentation externe nécessaire — juste la référence de travail entre l'utilisateur et l'agent pour la suite du développement (usage interne, pas de public).
- (decision) Paradigme retenu : Local-First. Dexie/IndexedDB est la source de vérité immédiate pour toute écriture ; un moteur de synchronisation dédié pousse vers Supabase en arrière-plan. Règle absolue : aucune écriture directe vers Supabase depuis l'UI, tout passe par Dexie d'abord. Choisi plutôt qu'une architecture couches classiques + file d'attente greffée, jugée moins rigoureuse (rien n'empêcherait un futur développeur d'appeler Supabase directement).
- (decision) Résolution de conflit local-first : au niveau du CHAMP, pas de la fiche entière. Chaque champ modifiable après coup (statut, priorité, transcription, description) porte sa propre métadonnée 'dernière modification de ce champ' (pas un doublon permanent de la valeur, juste un horodatage supplémentaire par champ concerné). Deux appareils modifiant des champs différents de la même fiche hors ligne ne créent jamais de conflit (les deux changements s'appliquent). Seul un vrai conflit (même champ modifié différemment sur les deux appareils avant sync) déclenche un état visible sur la fiche ('conflit de synchronisation — à vérifier', même mécanique que le badge nouveau) : les deux valeurs sont conservées temporairement le temps que l'utilisateur tranche en ouvrant la fiche, puis une seule valeur persiste. Aucun écrasement silencieux. Nécessite un ajout à EXPERIENCE.md (nouvel état + indicateur) en réconciliation.
- (decision) RÉVISION de l'hébergement par rapport à la spec technique initiale (qui prévoyait Vercel) : bascule sur Render (Web Service) pour l'hébergement Next.js App Router, et Render Cron Jobs pour déclencher les rappels/notifications push (remplace l'option Vercel Cron envisagée). Raison : l'utilisateur héberge déjà une autre application sur Render (même flux de déploiement, plateforme déjà connue), et Render convient bien à un outil interne (vérifié : support complet App Router incluant route handlers/server actions/middleware via Web Service ; Cron Jobs disponibles dès ~1$/mois). Vercel n'est plus retenu.
- (decision) Frontières de dépendance et arborescence : app/ (routes Next.js), domain/ (règles métier pures), data/local/ (Dexie), data/remote/ (client Supabase), sync/ (moteur de synchro + résolution de conflit par champ), components/ (UI). Règle : app/ et components/ ne parlent jamais directement à data/remote/ — tout passe par domain/ puis sync/. Seul le code serveur (route handlers, Cron) parle directement à Supabase, car jamais hors ligne.
- (decision) Stockage de fichiers hors ligne : Blob stocké directement dans Dexie jusqu'à l'upload vers Supabase Storage par le moteur de sync. Demande de stockage persistant navigateur (navigator.storage.persist()) pour réduire le risque d'éviction, notamment sur iOS.
- (decision) Sécurité : Row Level Security (RLS) Supabase sur chaque table, restreignant l'accès au propriétaire (auth.uid()), même en mono-utilisateur — pas de confiance aveugle dans le code client. Cohérent avec l'exigence de confidentialité des documents (PRD Cross-Cutting NFRs).
