# Story 3.2: Écriture hors ligne et synchronisation automatique

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a Guillaume,
I want que toute capture fonctionne sans connexion et se synchronise seule au retour du réseau,
so that je ne perde jamais une idée capturée hors ligne.

## Acceptance Criteria

1. **Given** aucune connexion réseau disponible **When** je capture une tâche **Then** elle est stockée localement (Dexie) et mise en file d'attente, sans blocage ni message d'erreur.
2. **Given** des éléments en attente de synchronisation **When** la connexion réseau revient **Then** la file se synchronise automatiquement avec Supabase, sans action de ma part.
3. **Given** n'importe quel écran **When** l'état de synchronisation change **Then** un indicateur discret et permanent affiche l'état courant (à jour / en attente / en cours).
4. **Given** plusieurs tentatives de synchronisation infructueuses pour un même élément **When** l'échec persiste **Then** l'indicateur passe à un état "Non synchronisé — toucher pour réessayer" ; la donnée reste visible et intacte localement.

- [x] Task 4: Schéma Supabase — tables `projects`/`tasks` avec RLS (AC: #2 ; AD-4)
  - [x] Guillaume exécute cette migration SQL dans l'éditeur SQL Supabase du projet dédié (`pxdmtnysvglorwchwsmc`, cf. Story 1.1) — **aucune table n'existe encore côté Supabase pour `Project`/`Task`**, seule l'infrastructure Auth existe à ce jour :
    ```sql
    create table public.projects (
      id uuid primary key,
      user_id uuid not null default auth.uid() references auth.users(id),
      name text not null,
      description text not null default '',
      color text not null,
      status text not null,
      created_at timestamptz not null
    );
    alter table public.projects enable row level security;
    create policy "projects_owner" on public.projects for all
      using ((select auth.uid()) = user_id) with check ((select auth.uid()) = user_id);

    create table public.tasks (
      id uuid primary key,
      user_id uuid not null default auth.uid() references auth.users(id),
      project_id uuid references public.projects(id) on delete set null,
      title text not null,
      description text not null default '',
      due_date timestamptz,
      reminder_at timestamptz,
      priority text not null,
      status text not null,
      provenance text not null,
      is_new boolean not null default true,
      created_at timestamptz not null
    );
    alter table public.tasks enable row level security;
    create policy "tasks_owner" on public.tasks for all
      using ((select auth.uid()) = user_id) with check ((select auth.uid()) = user_id);

    grant select, insert, update, delete on public.projects to authenticated;
    grant select, insert, update, delete on public.tasks to authenticated;
    ```
  - [x] **Correctif découvert en vérification manuelle** : le SQL ci-dessus incluait initialement les deux `grant` en dernier — sans eux, toute requête (même conforme aux policies RLS) échoue avec `permission denied for table ...` (Postgres exige un GRANT au niveau table **en plus** des policies RLS ; RLS restreint des lignes auxquelles l'accès est déjà permis au niveau table, il ne l'accorde pas lui-même). Piège classique de l'éditeur SQL Supabase : le Table Editor du dashboard applique ces grants automatiquement, une migration SQL brute non. Les deux lignes `grant` font désormais partie intégrante de la migration ci-dessus (bloc déjà mis à jour) — ne pas les omettre si cette migration est rejouée sur un nouvel environnement.

## Dev Notes

**Portée délibérément restreinte — ce que cette story NE fait PAS, et pourquoi :**
- **Aucune résolution de conflit par champ (AD-3) n'est implémentée ici.** AD-3 exige, pour être appliqué intégralement, que chaque enregistrement `Task`/`Project` porte ses propres métadonnées `<champ>_updated_at`/`<champ>_synced_at` et que `sync/` compare l'état local à l'état distant champ par champ pour détecter un vrai conflit. Aucune AC de cette story ne teste un scénario à deux appareils modifiant le même champ hors ligne — c'est exactement le périmètre de la **Story 3.6** ("Résolution de conflit de synchronisation par champ"), qui existe comme story dédiée séparée dans `epics.md` précisément pour cette raison. Construire cette logique maintenant serait de la sur-anticipation non testée. Le pull de cette story (Task 7, `pullOnce`) est donc volontairement **en insertion seule** (`if (!existe déjà localement) alors insérer`, jamais d'écrasement d'une ligne locale connue) — cette restriction est ce qui rend le pull sûr **sans** avoir besoin de la comparaison de conflit d'AD-3 : une ligne jamais vue localement ne peut jamais entrer en conflit avec une modification locale en attente.
- **`status: "synced"` et `status: "conflict"` de l'enveloppe ne sont jamais produits par le code de cette story** — `"synced"` est remplacé par la suppression pure et simple de l'entrée de file (Task 2, `markSucceeded`) : une fois poussée avec succès, l'entrée n'a plus d'utilité pour la Story 3.2 (elle en aurait une pour un futur historique/audit, non demandé). `"conflict"` est le statut que produira la Story 3.6 quand elle implémentera la détection réelle. Les deux valeurs restent dans le type `SyncStatus` de `domain/sync.ts` pour rester fidèle à l'énumération de la spine (le "Deferred" de `ARCHITECTURE-SPINE.md` laisse le schéma exact au code, mais l'énumération de statuts de la convention n'est, elle, pas un détail laissé libre).
- **`Note`/`Document` sont exclus de l'union `SyncEntity`** (restreinte à `"project" | "task"`) — ces entités n'existent pas encore dans `domain/` (Epic 5/Epic 6 les créeront). Étendre l'union quand ces entités existeront réellement, pas avant (même philosophie que Story 3.1 pour la portée du type "Tâche" à l'étape 3 de la capture).

**Répartition client/serveur du dossier `sync/` — lit `ARCHITECTURE-SPINE.md` littéralement, pas juste le diagramme Mermaid :** le diagramme structurel de la spine ne dessine qu'une arête `sync -.-> dataRemote` (pointillé, "contexte serveur uniquement") sans détailler comment un seul dossier peut à la fois dépendre de `data/local/` (disponible seulement côté client/IndexedDB) et de `data/remote/` (interdit côté client par la garde `server-only`). La résolution retenue ici, cohérente avec le texte d'AD-2 ("`data/remote/` ne peut être importé — directement ou transitivement — que par du code qui ne s'exécute jamais dans le bundle client") : `sync/` contient deux fichiers à committee de dépendance disjoints — `sync/client.ts` (importé par `app/sync-engine.tsx`, un composant `"use client"` ; dépend de `data/local/`, jamais de `data/remote/`) et `sync/server.ts` (importé uniquement par les deux route handlers de la Task 6, qui s'exécutent exclusivement côté serveur ; seul fichier de tout `sync/` à importer `data/remote/`). Aucun fichier de `sync/` n'est jamais importé à la fois par un composant client et par un route handler — la garde `server-only` de `data/remote/client.ts` continue de faire échouer le build si cette séparation était accidentellement violée.

**`app/` peut dépendre de `sync/` malgré son absence du diagramme Mermaid et de la liste explicite d'AD-2 ("`app/` dépend de `domain/`, `components/`, et `data/local/`") :** cette phrase d'AD-2 est immédiatement suivie de sa justification entre parenthèses — "*seule dépendance directe à une implémentation de stockage autorisée pour `app/`*" — elle ne parle que du choix entre `data/local/` et `data/remote/` comme **implémentations de stockage**, pas d'une liste exhaustive de tout ce que `app/` peut importer. `sync/` n'est pas une implémentation de stockage (c'est un moteur), cette restriction ne s'y applique donc pas. Sans cette lecture, rien dans l'architecture ne pourrait jamais déclencher le moteur de synchronisation depuis l'UI — la lecture retenue est la seule cohérente avec le fait que `sync/` doit être appelable. Documenté ici explicitement pour que la prochaine story qui touche `sync/`/`app/` ne redécouvre pas cette ambiguïté.

**Une entrée de file par champ à la création — décision volontairement suivie à la lettre malgré son coût apparent :** la convention de `ARCHITECTURE-SPINE.md` est explicite et non ambiguë : "`create` porte la valeur initiale de chaque champ (une entrée par champ, pas un instantané unique)". Cela produit ~10 entrées de file pour une seule tâche capturée. C'est intentionnel côté architecture (grain uniforme quel que soit `create`/`update`, nécessaire à la Story 3.6 pour comparer n'importe quel champ individuellement, y compris ceux fixés à la création). Le coût est absorbé côté efficacité réseau par `sync/server.ts` (Task 6), qui **fusionne** les champs d'un même `(entity, entityId)` en un seul upsert Postgres — le grain fin ne coûte qu'en lignes IndexedDB locales (négligeable), jamais en aller-retours réseau.

**Aucun type partagé entre `sync/client.ts` et `data/remote/` — duplication délibérée des interfaces de ligne distante :** `RemoteProjectRow`/`RemoteTaskRow` (Task 5) sont définies dans `data/remote/sync.ts`, un fichier qui importe transitivement `data/remote/client.ts` (gardé `server-only`). Même un `import type` isolé depuis `sync/client.ts` vers ce fichier créerait une dépendance de module (résolue par le bundler avant l'effacement des types), rouvrant le risque qu'un outil de build moins strict inclue malencontreusement le module `server-only` dans le bundle client. `sync/client.ts` définit donc ses propres interfaces locales (`PulledProjectRow`/`PulledTaskRow`, Task 7) pour typer la réponse JSON de `/api/sync/pull` — une petite duplication de forme, pas un partage de dépendance, qui garde la frontière client/serveur imperméable même à l'inspection du graphe de types.

**Pas de nouvelle dépendance npm.** `liveQuery` fait partie du paquet `dexie` déjà installé (4.4.4) depuis Dexie 4 — ne pas ajouter `dexie-react-hooks` uniquement pour un hook React de confort, `useSyncExternalStore` (React 19, déjà utilisé implicitement par le framework) suffit à faire le pont entre `liveQuery(...).subscribe()` et un composant React. `fetch` natif suffit pour les appels à `/api/sync/push`/`/api/sync/pull` (même origine, pas de client HTTP dédié nécessaire).

**Comportement de `proxy.ts` sur `/api/sync/*` non modifié délibérément :** son matcher actuel (liste d'exclusion des assets statiques) ne couvre pas `/api/sync/`, donc ces routes restent protégées comme toute autre route de l'app — une session expirée y déclenche une redirection 30x vers `/login` plutôt qu'un 401 JSON propre. Corriger `proxy.ts` pour distinguer les routes API des routes de navigation (401 vs redirection) serait une amélioration réelle mais hors périmètre des AC de cette story (aucune AC ne teste le comportement en session expirée) — `sync/client.ts` reste défensif (try/catch autour du parsing JSON) précisément pour absorber ce cas sans crash, sans avoir besoin de corriger `proxy.ts`. Un point différé peut être noté dans `deferred-work.md` si la review le juge pertinent.

**`createTask`/`createProject` passent désormais par une transaction Dexie incluant `syncQueue` — changement de comportement par rapport à Story 3.1/2.1 :** `createTask` n'utilisait aucune transaction (Story 3.1, "pas de lecture préalable requise") — ce n'est plus vrai : l'écriture de la tâche et la mise en file doivent être atomiques (une tâche écrite sans être mise en file ne serait jamais synchronisée ; une mise en file sans tâche correspondante n'a pas de sens). `createProject` avait déjà une transaction sur `db.projects` seul (pour la rotation de couleur) — l'élargir à `db.syncQueue` est un ajout mineur à un pattern existant.

**Référence croisée avec `deferred-work.md` (revue Story 3.1) :** le point différé "`createTask` persiste `projectId` sans vérifier que le projet référencé existe encore/est actif" mentionnait explicitement "à traiter si Story 3.2 introduit un chemin de résolution plus général pour ce type de référence obsolète" — **ce n'est pas le cas ici** : cette story ajoute une file de synchronisation, pas une validation de cohérence référentielle au moment de la capture. Le point reste différé tel quel, ne pas le traiter dans cette story (hors périmètre des AC).
